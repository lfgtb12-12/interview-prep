Bounded Agent Loops, Deadlines & Failure Recovery

An agent that can call tools is useful. An agent that knows when to stop—and what not to retry—is deployable.

Imagine a research agent with a ten-minute service-level deadline. It can query inventory, inspect recent delivery events, and draft a support reply. A model keeps asking for the same inventory lookup because it never sees what it wants. Meanwhile each tool consumes latency and money. One inventory update times out. Should the runtime repeat it? The difference between a demonstration and a production controller is how it handles these limits and uncertainty.

Memory hook: Bound the loop; budget the clock; distinguish retryable reads from ambiguous writes; preserve a truthful terminal status.

1. The five stop conditions

Step budget

Cap model/tool iterations even when every call returns successfully. A loop is not progress.

Absolute deadline

Carry one monotonic deadline from request admission through tool calls and response finalization.

Money and tokens

Account for provider/model usage and tool costs; stop before the budget is exhausted.

No new information

Track normalized tool proposals or evidence IDs. Repeated calls with unchanged evidence signal stalling.

Safety and uncertainty

Reject unauthorized calls. Never treat ambiguous side-effect timeouts as confirmed failure.

Deadline design: request deadline = monotonic start + total allowance. Before every operation, calculate remaining time, reserve finalization time, and pass a smaller timeout to the tool. A timeout parameter is only a promise if the underlying client actually enforces it.

3. Four different retry decisions

429 / 503 on a read

Usually retryable within deadline, with bounded exponential backoff and jitter; respect Retry-After. Still check contract-specific semantics.

Invalid JSON arguments

Do not repeat the tool request unchanged. Return a validation error to the model or stop after a bounded correction attempt.

Timeout on a read

If the operation is read-only, a retry may be appropriate if remaining budget permits.

Timeout on a payment/email

Outcome is UNKNOWN. Query server state or reuse the same operation key only when the service guarantees deduplication. Otherwise escalate.

Design retry at the layer that knows whether the operation is safe and how to reconcile. Multiple nested retry layers multiply traffic and may violate your global deadline.

4. Runnable Python controller lab

Save this as bounded_agent.py. Run python3 bounded_agent.py. Python 3.11+, standard library only. The clock and model are fake so tests are deterministic; replace them with real adapters only after you have explicit timeout and authorization contracts.

from dataclasses import dataclass
from typing import Callable

@dataclass
class Budget:
    max_steps: int = 4
    deadline_s: float = 8.0
    final_reserve_s: float = 1.0

def run(model: Callable, tool: Callable, clock: Callable, cfg=Budget()):
    start = clock()
    observations = []
    seen = set()
    for step in range(cfg.max_steps):
        left = cfg.deadline_s - (clock() - start)
        if left <= cfg.final_reserve_s:
            return {"status": "PARTIAL", "reason": "DEADLINE",
                    "observations": observations}
        proposal = model(observations)
        if proposal["kind"] == "final":
            return {"status": "SUCCEEDED", "answer": proposal["answer"]}
        if proposal.get("kind") != "tool" or proposal.get("name") != "lookup":
            return {"status": "FAILED", "reason": "TOOL_NOT_ALLOWED"}
        key = (proposal["name"], proposal.get("order_id"))
        if key in seen:
            return {"status": "PARTIAL", "reason": "NO_PROGRESS"}
        seen.add(key)
        timeout_s = max(0, cfg.deadline_s -
                        (clock() - start) - cfg.final_reserve_s)
        if timeout_s <= 0:
            return {"status": "PARTIAL", "reason": "DEADLINE"}
        # Production tool must enforce timeout_s itself.
        result = tool(proposal["order_id"], timeout_s)
        observations.append(result)
    return {"status": "PARTIAL", "reason": "STEP_LIMIT",
            "observations": observations}

def test_success():
    def model(obs):
        return ({"kind": "final", "answer": "Grounded"}
                if obs else {"kind": "tool", "name": "lookup",
                             "order_id": "A123"})
    answer = run(model, lambda key, timeout: {"id": key},
                 lambda: 0.0)
    assert answer["status"] == "SUCCEEDED"

def test_loop_breaker():
    m = lambda obs: {"kind": "tool", "name": "lookup",
                     "order_id": "A123"}
    answer = run(m, lambda key, timeout: {"id": key},
                 lambda: 0.0)
    assert answer["reason"] == "NO_PROGRESS"

def test_deadline():
    m = lambda obs: {"kind": "tool", "name": "lookup",
                     "order_id": "A123"}
    times = iter([0.0, 7.5])
    assert run(m, lambda a,b: {}, lambda: next(times))["reason"] == "DEADLINE"

if __name__ == "__main__":
    test_success()
    test_loop_breaker()
    test_deadline()
    print("3 deterministic controller tests passed")

Important limitation: this scaffold demonstrates step/deadline/no-progress decisions; it does not implement retries, persistent state, provider usage accounting, tool authorization, or cancellation. In a real controller, untrusted proposals must pass Chapter 2's schema and authorization gates. Python function timeouts are not preemptive by themselves.

Lab A · Add deterministic transient-read retries (solution sketch)

Wrap only the read adapter with a bounded retry loop. Catch a typed temporary error, check the global monotonic deadline before sleeping, use capped exponential backoff with jitter, and stop if there is not enough time for another attempt plus finalization. Inject a fake sleep and clock in tests; assert maximum attempts and that 403/schema errors are never retried.

Lab B · Add UNKNOWN state for writes (solution)

Separate read and write adapters. For a payment request, write an operation record with a stable idempotency key before dispatch; on ambiguous timeout, persist UNKNOWN and reconcile against the provider. Never automatically issue a new payment with a new key. Require policy authorization and, where applicable, human approval before execution. If the provider cannot reconcile, route to manual review.

5. Mid-level interview exercises

Exercise 1 · Budget invariants

In the controller above, identify why checking elapsed time only before the model request is insufficient. How would you bound the model call and ensure you still have time to serialize a final response?

Reference answer

Recompute remaining time at each boundary: admission, model invocation, validation, tool invocation, retry/backoff and finalization. Wrap model and tool HTTP clients in real timeouts, use a cancellation deadline where supported, and reserve a fixed finalization margin. If there is insufficient time, return a structured PARTIAL status with available evidence.

Exercise 2 · Tool-call fan-out

One model response requests eight tools in parallel. Your per-agent limit is four steps. Does this count as one or eight? Explain what you would meter.

Reference answer

Define distinct budgets: model turns, tool invocations, concurrent tool slots, time, tokens and money. A response with eight tool calls may be one model turn but eight tool invocations. Validate each call; cap fan-out independently. Reserve capacity and prevent an entire batch from bypassing tool limits.

6. Senior system design: research at scale

Design a research agent processing 10,000 requests per hour with a ten-minute end-to-end deadline. It invokes search providers, an LLM, a data warehouse and an optional report publication API.

Admission & backpressure

Bound queue depth and concurrent runs per tenant; reject or defer overload. Queue wait counts against the SLA.

Durability

Checkpoint completed evidence and operation keys. Use conditional ownership updates and fencing for state writes, not as a substitute for external deduplication.

Degradation

Reserve time for finalization; return a clearly labeled partial report if evidence is incomplete. Never invent missing sources.

Observability

Trace each step, tool latency, retry count, error category, evidence coverage, unknown side effects, cost, and completion status.

Senior follow-up: a publish request times out as the worker lease expires

The external publication might already have occurred. The new worker must load durable operation state, reconcile by operation key or query published artifacts, and avoid issuing a second unprotected publish. Fencing protects internal state from stale workers but does not undo already-sent requests. If no reliable reconciliation exists, persist UNKNOWN and require operator review.

Senior follow-up: how would you evaluate stop policies?

Run a trace replay and shadow comparison on representative inputs. Measure success, evidence coverage, p95 latency, spend, unnecessary tool calls, false no-progress stops, and duplicate-effect incidents. Segment by task difficulty. Avoid optimizing a low cost metric at the expense of grounded task success.
