RAG & Information Retrieval · Lesson 4

Hybrid Retrieval, Reranking & Query Rewriting

The right runbook exists, but search puts it on page two. Learn to rescue exact error codes and paraphrased questions without sacrificing permission checks, speed, or evidence quality.

What you'll build

We continue the internal engineering runbook assistant. You'll compare lexical, semantic and fused rankings; change a weighted RRF strategy; observe reranking change top-k evidence; and debug a missed payment runbook. The Python lab models the same ranking mechanics with deterministic scores.

Authorize and filter→BM25 + dense candidates→RRF / dedupe→Cross-encoder rerank→Top-k cited evidence

All demo rankings and reranker scores are hand-authored to illustrate mechanisms, not live model output. Real retrieval performance requires experiments on labeled data.

1. Why vector search misses

An engineer asks: “What does PAY-503 mean during a charge timeout?” A dense retriever might return a general timeout guide rather than the exact PAY-503 incident runbook. Embeddings are excellent at paraphrases but not guaranteed to respect rare identifiers, versions, or negation. A keyword retriever is often the better first step for exact tokens. Neither is sufficient alone: the runbook might say “ambiguous outcome” while the engineer asks “did my charge go through?” The two retrieval families complement each other.

We first apply trusted authorization and service filters to searchable candidates. Blending scores never grants access to a document. If a runbook is not indexed, no clever ranker can recover it.

2. BM25: reward rare matching terms

Lexical retrieval counts matching words, with extra credit for a term that appears in fewer documents. BM25 uses term frequency saturation (repeating a word forever should not increase its value linearly), inverse document frequency (rare words are informative), and document-length normalization (long documents shouldn't win merely because they contain more words). This is a bag-of-words method: it does not understand a synonym unless the indexing or query process adds one.

For term t in document d, a standard BM25 contribution is IDF(t) × tf(t,d)×(k1+1) / (tf(t,d)+k1×(1−b+b×|d|/avgdl)). One commonly used smoothed IDF is ln(1+(N−df(t)+0.5)/(df(t)+0.5)). k1 tunes saturation; b tunes length normalization. Tokenization, stemming, code symbols and field boosts matter in real indexes. Default settings are starting points, not universal constants.

3. Hybrid retrieval: combine candidates, not incompatible scores

Run the lexical and semantic searches on authorized documents. Each returns a ranked candidate list. Instead of adding raw BM25 and cosine scores—which have unrelated scales—Reciprocal Rank Fusion (RRF) adds weighted reciprocal ranks: wL/(k+rankL) + wS/(k+rankS). An absent document contributes zero for that list. The constant k (often 60) limits how much the first rank dominates. Weights tune preference; use a judged query set rather than intuition.

The interactive simulator uses deliberately authored rankings, not a live embedding or BM25 engine. Change the lexical weight and watch reciprocal-rank contributions update. A rank position describes relative order, not probability of relevance. Candidate depth matters: if neither branch retrieves the right document, fusion cannot invent it.

4. Reranking: spend more compute on fewer results

The first stage is designed for broad, cheap recall. A bi-encoder typically embeds questions and documents separately, allowing indexed nearest-neighbor retrieval. A cross-encoder reads a question-document pair jointly, capturing fine-grained interactions but requiring a separate inference per candidate. A practical design collects perhaps 30–100 candidates, merges duplicates, reranks those, then sends only a small top-k to generation.

Rerankers can fix ordering, not missing candidates. They add latency and inference cost, and their scores are model-dependent rather than calibrated truth. Apply the authorization boundary before either model sees restricted text. Deduplicate overlapping chunks and diversify by source where appropriate so five near-identical paragraphs do not crowd out other evidence.

5. Rewrite difficult questions carefully

Acronym expansion can turn “PAY-503 charge replay” into “PAY-503 payment charge retry idempotency replay.” Query decomposition turns “How do I retry and what if the status is unknown?” into subquestions about retry safety and ambiguous outcomes, then combines their evidence. HyDE-style approaches can draft a hypothetical answer for embedding-based retrieval, but generated details are untrusted search hints, never cited evidence.

Every rewrite should preserve identifiers, negation, tenant/service scope, time constraints, and user intent. Use a budget on variants and compare against an unchanged-query baseline. Expansion can drift toward the wrong service; decomposition increases requests, latency and merging complexity. An LLM rewrite is not required for every question—simple deterministic normalization or a synonym dictionary may suffice.

6. What to measure before launching

Use labeled queries and relevant source IDs. Recall@k asks whether relevant evidence was retrieved in the candidate pool; precision@k measures how many top results are relevant; MRR rewards early discovery of the first relevant passage; nDCG accounts for graded relevance and position. Always define whether labels are passage-level or document-level, and measure per query category (exact error codes, paraphrases, multi-hop, stale versions).

Measure each stage: authorized candidate recall, fusion recall, reranked nDCG@k, answer support, and citation correctness. Track p50/p95 latency, lexical/vector/reranker time, token cost, and index freshness. Tune weights, branch depth and reranker batch size against quality/latency budgets. Benchmark with the same ACL restrictions as production.

7. Debug an evidence miss systematically

If PAY-503 never appears: confirm source ingest/revision and access policy first. If it is indexed and permitted but absent from both candidate lists: check tokenizer and vector embedding, query analysis, filters and branch depth. If retrieved but ranked sixth while top-k is four: inspect RRF weights and reranker calibration; add relevant evaluation examples. If the source reaches the prompt but the answer is wrong: troubleshoot context assembly, citation mapping and generation—not search.

A safe fallback should say retrieval is unavailable when a branch is down, rather than claiming no policy exists. Log query class, policy revision, source IDs, per-branch ranks, fusion contributions, reranker version and timings, with sensitive text redacted. Check revocation at the trusted boundary and before final context assembly, including caches.

Interview practice: answers you can actually say aloud

Mid-level: Why hybrid search instead of only embeddings?

“I'd start by separating two needs. The runbook assistant has exact terms like PAY-503, where keyword search is reliable, and natural-language questions where embeddings help with synonyms. I'd retrieve authorized candidates from both, deduplicate them, and combine their rank positions with RRF rather than add raw scores from incompatible scales. Then I'd evaluate recall on our actual runbook questions, especially rare error codes. If the evidence doesn't make it into the candidate pool, the later answer model can't fix it.”

Senior-level: Design production retrieval and explain your trade-offs.

“I'd build a two-stage pipeline. First, I would enforce tenant and document authorization in the retrieval layer, then run BM25 and dense retrieval within that eligible corpus. I'd merge the lists with weighted RRF and deduplicate source chunks. I'd use a cross-encoder only on a bounded shortlist so we get better relevance without paying pairwise inference across the corpus. I'd measure authorized recall at the candidate stage, nDCG and precision after reranking, and cited-answer support downstream. I'd break metrics out for exact identifiers, paraphrases and multipart queries, alongside p95 latency and cost. If the right document disappears, I'd trace whether it failed ingestion, filtering, candidate retrieval, fusion, or context selection. If a backend is unavailable, I'd surface that explicitly rather than manufacture confidence. Rewrite expansion would be optional and controlled, because changing identifiers or negation can silently change the request.”

Follow-up: How do you decide whether rewriting is worth it?

“I'd test a baseline without rewriting, then compare targeted abbreviation expansion and decomposition on labeled ambiguous questions. I'd preserve codes, scope and negation, cap variant fan-out, and measure marginal recall against additional latency and cost. If rewriting increases wrong-service hits, I'd roll it back for that query category.”
