RAG & Information Retrieval · Lesson 2

Embeddings, Similarity & Vector Search

How can search find a runbook even when the question uses different words? Explore the geometry behind semantic retrieval, see when similarity metrics disagree, and learn what changes when you scale to millions of passages.

By the end of this chapter

  • Explain embeddings and the limits of semantic similarity in everyday language.
  • Calculate and compare dot product, cosine similarity and squared Euclidean distance.
  • Explain exact versus approximate nearest-neighbor retrieval and its trade-offs.
  • Recognize stale indexes, incompatible embedding versions, filtering errors and retrieval misses.

1. What does an embedding really represent?

Imagine two engineers asking “How should payment retries work?” and “What is the policy for retrying a failed payment request?” The phrases differ, but their meaning overlaps. Keyword matching can miss that relationship. An embedding model transforms each passage or question into a list of numbers called a vector. Models are trained so certain meaningfully related texts tend to occupy nearby regions in this mathematical space.

A vector might look like [0.8, 0.6, 0.0] in a toy three-dimensional example. Real embeddings often have hundreds or thousands of dimensions. Individual coordinates do not have reliable human-readable labels like “payment” or “retry.” The training objective, model and domain determine the patterns captured. You cannot assume every embedding model performs equally well for your team's acronyms or code.

Embedding similarity is a way to find candidates, not proof that the candidate answers the question. A policy document might be semantically similar but refer to the wrong service, version, or customer. Metadata filters, reranking and evidence validation still matter.

2. Three ways to compare vectors

A dot product multiplies corresponding coordinates and adds them. It is sensitive to both the direction and magnitude of the vectors. Cosine similarity divides the dot product by both vector lengths. It measures the angle between nonzero vectors: 1 for the same direction, 0 for perpendicular vectors, and -1 for opposite directions. Euclidean (L2) distance measures straight-line separation; smaller means closer.

Here's the interview trap: if you multiply a vector by ten, cosine similarity stays the same, but dot product and L2 distance can change substantially. For unit-normalized vectors, cosine similarity equals dot product and squared L2 distance equals 2 − 2 × cosine similarity. Under those conditions they produce the same ranking. Without normalization, do not assume that ranking equivalence.

Cosine is undefined for a zero vector. In real retrieval systems, check for invalid vectors, correct dimensions, model version compatibility and appropriate normalization before indexing or querying.

3. From embeddings to a vector search index

Offline ingestion produces embeddings for document chunks and stores them alongside chunk IDs, source versions, metadata and authorization information. At query time the application uses the same compatible embedding model to encode the question, then finds nearby chunk vectors. It retrieves the original text and provenance for selected IDs. Embedding a document does not automatically make it current; revised or deleted documents need reindexing and invalidation.

For a small collection, exact nearest-neighbor search compares the query vector to every authorized candidate. That's easy to reason about and useful as a correctness baseline, but it gets expensive at high scale. Approximate nearest-neighbor (ANN) indices trade exactness for speed and memory. Examples include graph-based HNSW and inverted-file approaches. Tuning affects recall, p95 latency, cost and update behavior.

Index choice is workload-specific. How many vectors? How frequently do permissions and documents change? Do filters have high selectivity? Do you need low-latency tail performance? A sophisticated ANN index is not automatically better than a small exact scan.

4. An end-to-end retrieval example

Our runbook assistant receives “What should we do for payment retries?” The application verifies the caller, selects only documents the caller can access, embeds the question, searches eligible vectors, and collects top candidates. The highest-scoring result could discuss transient reads, while another passage covers idempotent writes. Both matter because the question is broader than a single paragraph.

The retriever should log safe diagnostic identifiers: embedding model version, index revision, filter policy version, candidate IDs, scores and context IDs. It should not log sensitive runbook text indiscriminately. Results go to a context assembler where a separate answer-generation model cites appropriate sources. A near neighbor may still be wrong; reranking and answer support checks follow in later lessons.

Beware score thresholds: a cosine score of 0.78 is not universally “good.” Its meaning depends on the model, data distribution, preprocessing and task. Calibrate thresholds on labeled queries rather than inventing a constant.

5. When vector retrieval disappoints

A query for “503” can be more precise with keyword search than with embeddings. Likewise, exact service names, error codes and version strings often deserve lexical matching or metadata constraints. Dense retrieval captures some semantic relationships, but it may confuse closely related services or privilege general documentation over a rare critical runbook.

Debug systematically. If relevant text is missing from the index, fix ingestion. If it is indexed but far from the query vector, inspect your embedding model, input text, preprocessing and domain vocabulary. If it appears among candidates but not in final context, inspect top-k, filters and reranking. If the right evidence reaches the generator yet the answer misstates the policy, investigate generation and verification instead.

Measure recall@k on labeled question-to-relevant-passage pairs. Also track filter correctness, latency, embedding costs, index build lag and answer support. Do not use answer fluency as the only success signal.

6. Privacy, operations and migrations

Enforce document ACLs in trusted retrieval infrastructure before unauthorized text enters model context. Filtered ANN search may require special handling: post-filtering after an unfiltered top-k can produce too few results and may create privacy risks if forbidden content enters downstream processing. Validate your index's filter semantics, including permission revocation and cache invalidation.

Model migration deserves a deliberate plan. Embeddings from different models or incompatible versions usually cannot be compared meaningfully in one index. Dual-index a sample, compare offline recall and production latency, then migrate with rollback capability. Monitor for stale rows and failed deletions.

Global request deadlines, concurrency limits and bounded context sizes prevent embedding and vector search calls from monopolizing serving capacity. When the index is unavailable, explicitly return a retrieval-unavailable outcome; do not silently treat it as no matching evidence.

Interview-ready explanations

Mid-level: What are embeddings, and how would you use them for RAG?

“An embedding is a numeric representation of text that lets us compare meaning rather than relying only on exact words. I'd use the same compatible embedding model for document chunks and incoming queries, then find nearby chunks in a vector index. The retrieved text—not the vector itself—goes into the model's context along with source references. I'd still apply access filters and test retrieval quality, because a nearby vector is only a candidate match. It doesn't prove that a passage answers the question.”

Senior: How would you choose a similarity metric and search index?

“I'd first check the embedding provider's recommendation, including whether outputs are normalized, because that affects which metric makes sense. Cosine compares direction, while dot product also depends on vector magnitude. If vectors are unit-normalized, cosine, dot product and Euclidean distance give equivalent ordering. I'd establish an exact-search baseline on labeled questions, then evaluate an approximate index if the data size and latency require it. I'd compare recall at our context budget, filtered-query behavior, p95 latency, memory, ingestion cost and update performance. I wouldn't select HNSW or another ANN structure just because it's popular; the workload and security constraints should drive the decision.”

Senior follow-up: Retrieval is fast, but customers receive outdated answers. What's your debugging plan?

“I'd locate the first stale stage. I'd compare the source document revision to the indexed chunk revision and verify that updates, deletions and permission changes actually propagated. Then I'd trace the candidate IDs returned for the query, the passages selected for context, and the cited versions in the answer. If a model migration happened recently, I'd also check for mixed or incompatible embedding versions. Once we find the cause, I'd add freshness and recall regression checks, and make the user-facing system explicit when evidence is unavailable or stale. Faster vector lookup doesn't help if we're indexing the wrong facts.”
