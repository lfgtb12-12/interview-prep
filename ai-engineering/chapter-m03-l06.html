Agent Observability and Evaluation

Detailed draft lesson on agent observability and evaluation, with operational tradeoffs, failure scenarios, interactive teaching components and a Python-focused engineering exercise.

Learning objectives

  • Explain important correctness, observability, and reliability boundaries for production AI agents.
  • Design a deterministic test plan covering normal operation, adverse conditions and recovery.

Traces and causal debugging

A single successful HTTP response does not explain how an agent reached its answer. Assign a stable run identifier and trace the planning call, schema validation, tool selection, tool execution and answer evaluation as distinct spans. Each span should carry duration, attempt number, outcome, versioned policy identifier and useful evidence references. Correlation should cross process boundaries without placing credentials or private documents in logs. Track which retrieved records were offered to the model and which were cited in the final result. Debugging then becomes a question of finding the earliest stage where required information disappeared, rather than guessing from the prose of the response.

If ten incidents exist but the generated report mentions seven, count items at each pipeline boundary. Seven retrieved records indicate a collection or filter problem; ten retrieved but seven summarized points toward synthesis, truncation or an underspecified acceptance test. Instrument both pathways before rewriting prompts. Protect sensitive inputs with redaction, retention limits and restricted access to any debugging artifact.

Quality metrics are separate from uptime

Successful execution is not the same as task success. Track request success, deadline failures, p95 latency, tool-call costs and retry volume alongside groundedness, completeness and explicit task acceptance. Groundedness asks whether each checkable claim is supported by supplied evidence. Completeness asks whether all required aspects were covered. An answer with one accurate sentence can be fully grounded yet miss the main user request. Treat these dimensions separately rather than collapsing them into one arbitrary quality number.

Build scenario-based evaluation sets with difficult examples: missing evidence, conflicting documents, prompt injection in retrieved pages, slow APIs, uncertain writes and overlong inputs. A model-based evaluator can help at scale, but calibrate it against human-reviewed examples and review disagreement. Do not claim that a high score proves factual correctness when labels are weak or evidence itself is wrong.

Budgets and incident operations

An agent with a ten-second deadline cannot retry each tool for ten seconds independently. Pass remaining global time downstream, reserve final response time and cap tool rounds and concurrency. Retry safe transient reads using bounded backoff and jitter; do not automatically replay an uncertain write. Measure deadline-exhausted outcomes explicitly. Under load, admission limits protect the service from runaway agent loops and cascading provider throttling.

Define user-relevant service-level objectives, for example completed grounded reports within a fixed time window. Alert on high-severity omissions and unresolved UNKNOWN operations, not merely server crashes. Every alert should point to representative run IDs, the affected release, and the stage that failed, so the on-call engineer has a reproducible starting point.

Shadow runs and promotion gates

Before deploying a new model or prompt, replay the same evaluation inputs against the current baseline and candidate version. Compare coverage, hallucination rate, unsafe tool selection, latency distribution, token usage and failure-category counts. A lower median latency is not a success if rare critical omissions double. Preserve evidence snapshots and model parameters so differences are interpretable.

An operational checklist needs clear rollback thresholds. Review high-impact failures individually even if an average score improved. Label uncertainty openly: an evaluator is one component of an evidence-based release process, not the authority that defines truth.

Hands-on Python lab

Deterministic Python controller lab

  1. Implement a trace recorder and evaluator for a deterministic report agent. Create ten mock incidents, drop three at retrieval in one test and omit two during synthesis in another. Store stage counts and source IDs, assert coverage and groundedness separately, and test deadline exhaustion.
  2. Use standard-library unittest and include separate assertions for happy path, failure path, and ambiguous outcomes.
  3. Record an evidence-based expected result and keep external integrations mocked until reliability is demonstrated.

Expected outcome: A deterministic test suite distinguishes valid completion from missing evidence, ambiguous results, and failed recovery.

Runnable reference implementations and tests are available in ai-engineering/factory/labs/ and test_lesson_labs.py in the GitHub repository.

Senior interview practice

  1. Design a production architecture for this lesson, including durability, failure ownership, operational observability, and tenant separation.
  2. Explain which guarantees come from trusted application code versus model behavior and third-party API contracts.
  3. Develop measurable rollout criteria and failure-injection tests for rare but high-impact incidents.

Knowledge check

1. Which data best isolates the first failing stage?

2. What does a successful HTTP response establish?

3. What is safest when a write outcome is UNKNOWN?

4. Which claim about checkpointing is correct?

5. Why test rare critical errors separately?
