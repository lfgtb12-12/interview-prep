Agent Orchestration, State & Execution Patterns

An agent is more than a loop: it is a dependency-aware execution system that knows what ran, what is safe to repeat, and what must wait.

A report assistant must retrieve orders and inventory, synthesize evidence, then publish a report. Can the two lookups overlap? What if a worker crashes after publishing but before saving success? Who decides which step runs next—the model or the controller?

Memory hook: The graph defines dependencies. The state machine defines legality. Checkpoints define recovery. Trusted code enforces all three.

1. Orchestration vs model reasoning

Workflow

Code predefines each dependency. Prefer deterministic orchestration for stable business processes and auditability.

Agent-directed

A model suggests actions or branches, but the controller checks allowed transitions and budgets before execution.

Hybrid

A durable graph establishes mandatory gates; model nodes decide bounded substeps, such as query refinement.

A graph is a directed set of task dependencies. A DAG has no dependency cycles; cycles for iterative reasoning must be explicit, bounded controller transitions rather than accidental prerequisite loops. Schedulers compute the ready set: steps whose predecessors are all SUCCEEDED. Fan-out launches independent work; fan-in waits for required results.

Interview distinction: parallelism reduces critical-path latency, not necessarily total work or cost. More concurrency means higher provider load, bigger rate-limit risk and harder cancellation.

2. Interactive DAG execution simulator

Choose an execution strategy and a failure mode. Advance step by step or play the trace. The graph status, animated active edges, per-task timeline, and event log remain synchronized. Simulation is deterministic; no providers are called.

3. Durable state and legal transitions

A step is not just a Boolean “done”. Represent PENDING → RUNNING → SUCCEEDED, with alternative transitions to FAILED or UNKNOWN. FAILED is known non-success (for example, deterministic validation failure); UNKNOWN means execution may have happened but confirmation is missing. A retry decision depends on operation semantics and provider guarantees.

Checkpoint

Persist normalized inputs, output references, status, attempt, timestamp and operation key. Commit completed output and SUCCEEDED atomically where possible.

Claim

Workers acquire ownership with conditional writes, leases and fencing tokens to stop stale workers modifying durable state.

Reconcile

After a crash, reload state; skip successful steps. Before repeating side effects, query the provider by stable operation key or place UNKNOWN into a review queue.

Side effects require additional design: a database checkpoint alone cannot atomically commit an external email send. Use provider-enforced idempotency where available, or reconcile external status. If neither guarantee exists, do not automatically replay an ambiguous write.

4. Scheduling rules and tradeoffs

Sequential

Simple trace and deterministic ordering; critical path approximates sum of task times. Good when dependencies truly form a chain.

Parallel fan-out

Independent reads overlap. Bound each tenant and provider; pass deadlines into every worker and handle partial results explicitly.

Join policy

ALL waits for all required evidence. QUORUM can return useful partial results only when the business contract permits it, with missing evidence labeled.

Recovery

Durable status, deterministic keys and idempotent adapters allow a new worker to continue safely; unconfirmed external writes require reconciliation.

For order lookup 3 seconds and inventory lookup 4 seconds, synthesis 2 seconds, publication 1 second: sequential latency is about 10 seconds; independent parallel reads yield about 7 seconds before overhead. Maximum possible gain is bounded by the longest dependency chain (critical path). Real systems include queue wait, throttling and serialization.

5. Python lab: dependency-safe executor

Save the following as orchestration_lab.py and run python orchestration_lab.py. This standard-library example validates the graph, executes independent tasks concurrently, uses a teaching-only in-memory checkpoint and blocks ambiguous writes. It is not a crash-safe production scheduler: a real implementation must store status durably with atomic conditional transitions before dispatch and on completion.

"""Offline DAG runner. Python 3.11+; no external packages."""
from dataclasses import dataclass, field
from concurrent.futures import ThreadPoolExecutor, wait, FIRST_COMPLETED
from typing import Callable

@dataclass(frozen=True)
class Task:
    deps: tuple[str, ...]
    fn: Callable[[dict], object]
    side_effect: bool = False

@dataclass
class Store:
    # Teaching store: substitute transactional DB for production.
    status: dict[str, str] = field(default_factory=dict)
    result: dict[str, object] = field(default_factory=dict)

class UnknownOutcome(RuntimeError):
    pass

def validate(tasks: dict[str, Task]) -> None:
    for name, task in tasks.items():
        if name in task.deps or any(d not in tasks for d in task.deps):
            raise ValueError("invalid dependency")
    seen, active = set(), set()
    def visit(n):
        if n in active:
            raise ValueError("cycle")
        if n in seen:
            return
        active.add(n)
        for d in tasks[n].deps:
            visit(d)
        active.remove(n)
        seen.add(n)
    for name in tasks:
        visit(name)

def run(tasks: dict[str, Task], store: Store, workers=2):
    validate(tasks)
    if workers < 1:
        raise ValueError("workers must be positive")
    pending = set(tasks) - {n for n in tasks if store.status.get(n) == "SUCCEEDED"}
    running = {}
    with ThreadPoolExecutor(max_workers=workers) as pool:
        while pending or running:
            # Snapshot immutable dependency results before task submission.
            ready = sorted(n for n in pending if all(store.status.get(d) == "SUCCEEDED" for d in tasks[n].deps))
            for n in ready[:max(0, workers - len(running))]:
                if tasks[n].side_effect and store.status.get(n) in ("RUNNING", "UNKNOWN"):
                    raise UnknownOutcome(n + ": reconcile before replay")
                store.status[n] = "RUNNING"  # production: durable CAS before submission
                inputs = {d: store.result[d] for d in tasks[n].deps}
                running[pool.submit(tasks[n].fn, inputs)] = n
                pending.remove(n)
            if not running:
                raise RuntimeError("blocked by failed/unknown dependency")
            done, _ = wait(running, return_when=FIRST_COMPLETED)
            for future in done:
                n = running.pop(future)
                try:
                    value = future.result()
                except UnknownOutcome:
                    store.status[n] = "UNKNOWN"
                except Exception:
                    store.status[n] = "FAILED"
                else:
                    store.result[n] = value  # production: atomic result + status commit
                    store.status[n] = "SUCCEEDED"
            if any(store.status.get(n) in ("FAILED", "UNKNOWN") for n in tasks):
                # In-flight reads may finish; do not dispatch more downstream tasks.
                if running:
                    for future in running: future.cancel()
                raise RuntimeError("workflow stopped: inspect checkpoint")
    return store.result

def demo():
    tasks = {
        "orders": Task((), lambda _: ["o1", "o2"]),
        "inventory": Task((), lambda _: {"available": True}),
        "synthesize": Task(("orders", "inventory"), lambda v: {"evidence": v}),
        "report": Task(("synthesize",), lambda v: "report-ready"),
    }
    s = Store()
    assert run(tasks, s)["report"] == "report-ready"
    assert run(tasks, s)["report"] == "report-ready"  # completed steps skipped
    assert all(v == "SUCCEEDED" for v in s.status.values())

if __name__ == "__main__":
    demo()
    print("All assertions passed")

Deterministic unit tests

Save as test_orchestration.py, then run python -m unittest -v test_orchestration.py. No external API or LLM required.

"""Save alongside orchestration_lab.py; python -m unittest -v test_orchestration.py"""
import unittest
from orchestration_lab import Task, Store, UnknownOutcome, run

class TestOrchestration(unittest.TestCase):
    def test_dependencies_and_resume(self):
        calls = []
        tasks = {
            "a": Task((), lambda _: calls.append("a") or 3),
            "b": Task(("a",), lambda x: calls.append("b") or x["a"] * 2),
        }
        store = Store()
        self.assertEqual(run(tasks, store)["b"], 6)
        run(tasks, store)
        self.assertEqual(calls, ["a", "b"])

    def test_cycle_rejected(self):
        with self.assertRaises(ValueError):
            run({"a": Task(("b",), lambda _: 1),
                 "b": Task(("a",), lambda _: 2)}, Store())

    def test_unknown_write_never_replayed(self):
        calls = []
        def send(_):
            calls.append("sent")
            raise UnknownOutcome("acknowledgement lost")
        tasks = {"send": Task((), send, side_effect=True)}
        store = Store()
        with self.assertRaises(RuntimeError):
            run(tasks, store)
        self.assertEqual(store.status["send"], "UNKNOWN")
        with self.assertRaises(UnknownOutcome):
            run(tasks, store)
        self.assertEqual(calls, ["sent"])

    def test_failure_blocks_downstream(self):
        calls = []
        def fail(_): raise ValueError("provider error")
        tasks = {"read": Task((), fail), "publish": Task(("read",), lambda _: calls.append(1))}
        with self.assertRaises(RuntimeError):
            run(tasks, Store())
        self.assertFalse(calls)

if __name__ == "__main__":
    unittest.main()

Important nuance: Python threads may finish already-running work after an exception even if cancellation was requested. This teaching runner prevents downstream dispatch after a detected failure, but in-flight work is not a substitute for distributed cancellation, and the completion-commit is not atomic.

6. Mid-level coding and debugging exercises

Exercise A · topological scheduling

Add a new risk_check dependency before publication. Explain why launching publish when synthesis is RUNNING violates the invariant. Write a test showing that publish does not run when risk_check fails.

Solution and invariant

Set risk_check = Task(("synthesize",), ...); set report = Task(("risk_check",), ...). Readiness requires all(store.status.get(dep) == "SUCCEEDED" for dep in tasks[name].deps). Do not use “not failed” because PENDING and RUNNING are not successful evidence.

Exercise B · recover a stale RUNNING read

A worker dies while fetching inventory. The new worker observes RUNNING. What must change before this safe read can resume?

Reference approach

Use an expiring lease with ownership generation/fencing and a conditional transition to reclaim the step. A read-only or idempotent query may be retried within budgets after ownership recovery. Persist a fresh attempt record; never let an old worker commit stale results.

Debugging puzzle · publish twice

Production timeline: worker A sends publish; provider commits; response times out; A crashes. Worker B sees status RUNNING and issues publish again. Identify the design defect and safe response.

Solution

The local checkpoint could not prove remote failure. Treat outcome as UNKNOWN, check provider status using the same operation key, and only replay if provider enforces deduplication or non-execution is proven. Lease fencing protects internal updates, not external sends.

7. Senior-level architecture interview

Prompt: Design a multi-tenant research agent processing 10,000 runs/hour. Each run fans out to three retrieval providers and one evaluator, and may publish a report. End-to-end deadline 10 minutes; duplicate publication is unacceptable.

API & admission

Accept request ID and tenant ID; enforce quotas and bounded queue length; measure deadline including queue wait.

Execution

Durable coordinator; dependency-ready scheduler; provider-specific rate limits; fair tenant scheduling; explicit terminal status.

State & recovery

Transactional step records, immutable output references, unique operation IDs, versioned compare-and-swap and reconciler.

Observability & evals

Correlate run/step IDs; p95 latency, provider throttling, checkpoint failures, unknown writes, evidence coverage and cost.

Senior follow-up: AWS implementation

For a well-defined finite graph, Step Functions Standard plus Lambda/ECS workers and DynamoDB status can be a practical choice; Map/Parallel states coordinate bounded fan-out. SQS buffers admission, with per-tenant throttling. A custom worker coordinator is justified for highly dynamic graphs but adds scheduler complexity. Keep external publish behind an adapter with a durable idempotency key and reconciliation path. IAM controls service-to-service authorization; do not use it to infer the model is authorized to publish user-specific content.

Senior follow-up: consistency and failure isolation

Choose step output immutability, transactionally bind the result URI to SUCCEEDED, and only release dependents after commit. Allow independent branches to finish but label incomplete evidence. Retry safe reads with jitter and global deadlines; circuit-break overloaded providers. Never let speculative parallel branches bypass approval or access checks.

Interview-ready: orchestrating dependent agent work

Explain which decisions belong to the scheduler and which are appropriate for the model.

Mid-level answer

“I'd model the tasks as a dependency graph. If two lookups don't depend on each other, we can run them in parallel. But a step that summarizes both results has to wait for them. The scheduler, rather than the model's text, should decide which steps are ready and mark each result as completed. That makes it easier to understand failures and resume from a checkpoint.”

Senior answer

“I'd separate the durable workflow graph from the model's decisions inside individual steps. The orchestrator owns dependencies, state transitions, retry policy, and concurrency limits. A model can choose a bounded action within that structure, but it can't skip a mandatory dependency. I'd checkpoint results and claim work through conditional state updates so competing workers don't overwrite each other. On recovery, I'd replay safe reads but treat an ambiguous external write as UNKNOWN until the provider confirms the outcome. Finally, I'd trace the critical path and use backpressure to keep fan-out from overwhelming downstream services.”
