RAG & Information Retrieval · Lesson 3

Document Ingestion, Chunking & Metadata

A RAG assistant is only as trustworthy as the knowledge it can find. Learn how documents become searchable evidence—and why boundaries, versions, deletions and permissions matter as much as embeddings.

Objectives

  • Trace an ingestion pipeline from source document to searchable chunk.
  • Predict how chunk size and overlap change boundaries and duplication.
  • Design source provenance, document updates, deletions and ACL-aware metadata.
  • Test deterministic ingestion behavior and explain production trade-offs aloud.

At a glance: two paths

Ingestion: the system prepares source material ahead of questions.

Source revisions→Parse + structure→Chunk + metadata→Embed + index

Query: trusted authorization and retrieval use only permissible indexed content, then pass evidence to generation.

1. Why ingestion is more than uploading files

Imagine an engineer asks, “Can the payment worker retry an outbound charge?” Your search might return an old runbook even though the current version says retries require an idempotency key. That's not a language-model problem. The retrieval system is searching a stale copy of the knowledge base.

Ingestion is the process of turning real source material into searchable evidence. A useful pipeline discovers documents, extracts usable text, normalizes it, splits it into passages, attaches metadata and permissions, creates searchable representations, and publishes them to an index. It also handles the reverse direction: updates, deletions, and access revocations.

The most important mental model is that the search index is a derived view. Your source system remains authoritative. If a document changes at the source, the index must eventually reflect it—and sensitive access changes may require much faster enforcement than ordinary content updates.

2. Extract text without losing meaning

Real source material is messy: HTML pages, markdown files, PDFs, tables, code blocks, and scanned images. A parser can lose a heading, strip a table's column labels, or join sentences that belong to different sections. Before chunking, preserve meaningful structure and the original source reference.

For a runbook, keep headings such as “Read retries” and “Outbound writes” connected to their respective paragraphs. Otherwise a retrieved snippet saying “Retry with jitter” could be mistaken for permission to repeat a charge. For tables, include enough row and column context to interpret values correctly. For code, preserve function names, imports, and adjacent comments where useful.

Store extraction status and parser version. A document that parsed as blank should not quietly become a successful ingestion. Quarantine malformed files and surface ingestion failures so content owners can repair them.

3. Chunking: the trade-off you can see

A chunk is a passage small enough to search and include in the model's context. Smaller chunks often make retrieval more specific and cheaper per passage, but they risk separating a condition from its consequence. Larger chunks preserve surrounding explanation, but they can dilute relevance and consume more context.

Fixed-size chunking groups a certain number of tokens or words. Overlap repeats a small span between adjacent chunks so ideas near a boundary can be found from either side. For size six and overlap two, the starting positions are 0, 4, 8, and so on. That repetition increases index size and may create duplicate evidence. It doesn't repair a document whose structure has already been lost.

A production strategy often begins with structure-aware splitting—headings, paragraphs, tables, code blocks—then applies size limits and controlled overlap. Compare strategies on real labeled user questions instead of picking a magic chunk size. This page uses words for visual clarity; real token limits should use the target tokenizer.

4. Metadata gives evidence an identity

Each indexed chunk needs more than plain text. Record a stable document ID, revision, source URL or path, section heading, positional span, ingestion timestamp, language where useful, parser version, and permission or tenant scope. Use identifiers that let you trace a citation back to exactly the source passage and revision.

Metadata also narrows searches: an engineer asking about payments should be able to filter by service, environment, document type, and possibly an effective-date range. But filters must be tested: overstrict filters silently hide relevant passages, while loose tenant or ACL filters may expose information the user should not see.

A document's title and headings can improve embedding context, yet avoid copying misleading or sensitive metadata into a lower-trust environment. The text itself may contain prompt-injection instructions; ingestion does not make it trustworthy system guidance.

5. Updates, deletions, and permission revocation

Suppose revision 4 replaces revision 3 of a payments runbook. Simply adding revision 4 creates two competing answers. A robust indexer tracks source identity and revision, produces the new chunks, then swaps the indexed view while removing stale chunks. If processing fails, retain the last known state with an explicit freshness warning rather than claiming that the latest revision is present.

Out-of-order events are common in distributed systems. Reject a stale upsert or delete that would roll the index backward. A deletion needs a durable tombstone or equivalent version tracking; otherwise a delayed old upsert can resurrect removed content. The Python lab below is intentionally in-memory and does NOT provide durable tombstones or atomic transactions across a vector database and document store.

Authorization is even more urgent. Permissions must be enforced by trusted retrieval services, ideally against a sufficiently fresh authoritative ACL source for sensitive documents. Index rebuilds and long-lived caches are not a reliable sole mechanism for immediate revocation. Fail closed when an access check cannot be verified.

6. Design an ingestion pipeline that can recover

Separate ingestion jobs from online user queries. Use a durable queue or change feed, versioned document records, bounded workers, retry policy, a dead-letter path for poison documents, and a mechanism for full reconciliation. Make processing idempotent by source ID and revision, and guard against multiple workers racing on one document.

Instrument source event time, last indexed revision, queue lag, parser failures, chunk counts, embedding failures, denied-document retrieval attempts, and deletion lag. A successful worker HTTP response does not establish that a document is fully searchable; check the published index state. When using multiple storage systems, plan for partial writes and recovery.

Production evaluation should include real questions with known supporting passages. Track retrieval recall@k, stale-document hits, wrong-tenant exposure (which should be zero), answer citations and cost. Build a migration strategy for new parsers or embedding versions using side-by-side indexes and rollback. M04-L04 will show how retrieval ranking builds on this foundation.

Interview-ready answers

Speak these naturally; use a specific failure to explain the design, then mention trade-offs.

Mid-level: How do you ingest documents into RAG?

“I'd start by extracting the document content while keeping meaningful structure, like section headings, code blocks and table labels. Then I'd split it into searchable passages, attach source IDs, versions and permissions, and create embeddings for the chunks. The retrieval index would store enough metadata to point an answer back to the exact source. I'd also plan how updates and deletions replace old chunks, because a successful initial upload isn't enough if the documents keep changing. Finally I'd test retrieval using representative questions, not just check that vectors were written.”

Senior: Design a reliable ingestion service for changing internal documentation.

“I'd treat the search index as a derived view of an authoritative document system. I'd consume versioned change events through a durable queue, parse and chunk each revision, and stage the new index entries before publishing them. Each document would have a stable ID, source revision, metadata, and access policy. I'd use revision checks so delayed jobs can't overwrite newer versions, and I'd implement deletion handling with durable tombstones or equivalent safeguards. I'd monitor indexing lag, parser errors, stale documents and permission changes, with a reconciliation job to repair missed events. Because vector stores and metadata stores may not share a transaction, I'd design recovery for partially applied updates. For sensitive material, authorization is checked with sufficiently fresh trusted permissions at query time—not just the ACL snapshot stored during ingestion.”

Senior follow-up: Retrieval still cites an old deleted runbook. What would you do?

“First I'd verify which runbook revision is authoritative and trace the cited chunk ID back to its indexed revision. Then I'd inspect whether the delete or update event reached ingestion, whether workers processed it out of order, and whether caches or a second index still contain stale entries. I'd contain the issue by preventing outdated evidence from being used for high-impact answers, then repair the affected index records and run a full reconciliation. I'd add regression tests for stale updates after deletion and monitor deletion lag. If access was revoked, I'd treat it as a security issue and check authorization enforcement independently of the indexing delay.”
