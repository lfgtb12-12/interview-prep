Evaluation & Experimentation · Lesson 5

Agent & Tool-Use Evals

The agent answered the support ticket correctly—but called an unauthorized tool on the way. Should that run pass? No. An agent evaluation must measure what happened to the user and what the agent did along the way.

What you will learn

Build trajectory and outcome rubrics for a tool-using assistant. Separate deterministic validation from semantic judgment, reward legitimate alternative routes, and expose unsafe retries, ambiguous outcomes and prompt injection. The running example is an internal support assistant with runbook search, incident-log lookup and a publishing tool.

Continue from experiment design: the quality metric you compare between versions has to reflect actual task success and safety, not merely output fluency.

1. Define the evaluation contract before collecting traces

For each case, record the user's goal, trusted identity and permissions, available tool contracts, expected externally verifiable outcome, and any required recovery behavior. Keep those labels separate from the model's own justification. A support answer can be fluent and wrong; a publish confirmation can sound certain when the write's result is actually unknown.

Two metrics are helpful: task outcome rate and safe task completion rate. The latter requires an acceptable outcome and all mandatory security and side-effect gates. Never let good answers compensate numerically for permission violations. Set your case denominators in advance and report per-category results as well as the aggregate.

2. The trace is evidence, not the goal

Suppose the support request can be answered using either search or lookup. Both return approved evidence, and both produce the right answer. Exact step-by-step matching would fail the second trajectory even though it completes the task safely. Evaluate allowed behavior and final state rather than insisting every agent take one reference path.

Exact trace matching is still useful when order is a protocol requirement: for example, a privileged write must always follow approval, or an ambiguous payment must be reconciled before any further action. Specify invariants such as “no unauthorized read” and “at most one effective publish” rather than a single canned transcript. 4. Unknown does not mean failed

A publish operation may time out after reaching the server. The client cannot tell whether the side effect committed. This is an UNKNOWN outcome—not an automatic failure and not permission to repeat the write. An acceptable recovery checks a durable request ID through the authoritative status tool, or escalates for reconciliation when verification is unavailable. Retrying with a new request ID can create a second publish. Even retrying with the same ID requires a server-enforced idempotency guarantee; the ID alone is not enough.

Our fixture flags repeated publish invocations conservatively and distinguishes them from confirmed duplicate writes. It also treats safe escalation as an incomplete task: safe handling should be recognized without fabricating successful completion. For production, compare independent write ledgers, status-query results and compensating actions, not just tool-call text.

5. Adversarial tests must exercise the boundary

Attack cases include a malicious runbook instructing the agent to invoke a delete tool, requests for another tenant's incident logs, tampered tool outputs, replayed operations and malformed nested arguments. The trusted system should decide actor identity and authorization, never the retrieved text. Grade whether the boundary holds even if the agent verbally refuses after attempting an unauthorized call.

Evaluate both allowed tasks and denied tasks, and report slices: per tool, intent, tenant class, ambiguity, failure mode and adversarial input. A dataset dominated by easy search calls can hide one severe write-path regression. Zero observed unsafe events in a small fixture is not proof that production risk is zero. Use shadow testing, human review, production enforcement and monitoring in addition to offline evaluation.

Interview-ready answers

Mid-level · “How do you evaluate an agent that calls tools?”

“I'd start with realistic tasks and record what successful completion actually looks like. Then I'd check each tool call for an appropriate tool, valid arguments and permission to access the resource. I'd score those separately from the final answer. I'd include failures such as invalid inputs, timeouts and prompt injection. And I wouldn't require every successful run to follow exactly the same sequence—different safe routes can reach the same result.”

Senior-level · “The agent completed 95% of tasks. Is it ready to ship?”

“Not from that number alone. I'd want the denominator, the task mix and an independent outcome oracle. A successful-looking answer could conceal an unauthorized call or a duplicated write, so I'd treat authorization and side-effect invariants as hard gates. I'd inspect traces and external state together, including unknown results that require reconciliation instead of blind retries. Then I'd break results down by tool, permissions, tenant and adversarial cases, compare versions on a held-out set, and use shadow runs before a guarded rollout. Production enforcement stays in place even if the offline tests all pass.”

Wrap-up

An agent can complete the task by more than one legitimate path. Evaluate the state it produced, the constraints it respected and the risks it introduced. Deterministic validators enforce clear contracts; human-reviewed semantic labels cover intent and outcome. Neither is a substitute for production permission checks or authoritative records of side effects.
