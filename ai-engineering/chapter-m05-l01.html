Evaluation & Experimentation · Lesson 1

Evaluation Foundations: Datasets, Metrics & Failure Taxonomy

Your support agent gave a convincing but unsafe answer. How do you prove the next version is better before shipping it? We need labeled examples, a clear definition of success, and measurements that expose what averages hide.

Learning goals

Build a realistic evaluation dataset; separate answer correctness from answer coverage; tune a confidence threshold without violating security boundaries; identify false abstentions and risky answers; and explain a launch decision in an interview.

1. Collect real-like user questions
2. Adjudicate expected behavior
3. Run frozen candidate pipeline
4. Score outcomes by slice
5. Decide: ship, fix or investigate

1. Evaluation is a test, not a compliment

Imagine an internal assistant asked: “PAY-503 timed out. Can I replay the charge?” A fluent answer sounds reassuring, but it may recommend a duplicate payment. We need to check what the system actually did, against the current authorized runbook and a reviewed expected answer.

A golden set is a collection of test questions with human-adjudicated labels. For each case, record the query, expected evidence, whether a safe answer is possible, required behavior, acceptable factual claims and the reason for any refusal. Keep the evidence revision and caller permissions: the same question may require a different response after a policy update.

Failure taxonomy: candidate miss (retrieval never found evidence); context loss (reranker dropped evidence); unsupported or incomplete answer (generation or verification); false abstention (enough evidence existed); ACL violation (trust boundary); stale policy (ingestion); deadline or outage (operations). Different failures have different fixes.

2. Define denominators before calculating metrics

Answered-item accuracy is correct answers divided by all answers returned. Coverage is answered requests divided by all requests. Answerable coverage in our lab is correctly answered authorized-answerable requests divided by all authorized-answerable requests. Error rate per request counts unsafe/incorrect answers across all requests, including those that were unanswerable. No returned answers means answered-item accuracy is undefined, not 100%.

These measurements describe different trade-offs. A strict threshold can improve correctness among answered questions while denying useful answers to many users. It cannot rescue a missing document or a permission leak. Treat ACL enforcement, schema validation and redaction as hard gates in application code; do not trade them against average answer quality.

3. Build a holdout that represents your risks

Collect routine FAQs, rare payment error codes, ambiguous requests, insufficient-evidence cases, multilingual phrasing, revocations, contradictory document revisions and prompt injection examples. Label independently; adjudicate disagreements. Keep a development set for prompt and threshold tuning, a final untouched test set for release claims, and ongoing incident regressions. Watch for duplicates or training/test contamination.

An average can look good while PAY-503 performance collapses. Slice metrics by query type, customer or tenant policy, evidence freshness and retrieval failure. Report counts and uncertainty, especially for small rare-case slices. Ten authored rows below teach the arithmetic; they are not representative production data or calibrated confidence scores.

4. Metrics that answer different questions

Retrieval recall@k asks whether necessary source passages appeared among the top-k candidates. Citation precision asks whether cited passages actually support the claims attributed to them. Completeness asks whether material required facts were included. Correct abstention asks whether the system withheld unsupported answers; false abstention asks when it withheld a supportable one. Production SLOs cover p95 end-to-end latency, error budget, cost, and indexing freshness. None alone proves the assistant is safe.

Calibration: scores of 0.8 are not necessarily 80% probabilities of correctness. Calibration must be demonstrated on relevant held-out data and checked for distribution drift. A threshold policy should be chosen from development data using a documented risk budget, then measured on untouched examples with confidence intervals where appropriate.

5. Choose the right evaluation layer

Deterministic: ACLs, schemas, mandatory citations, duplicate side effects
Human-reviewed: intent, completeness, factual correctness and risk severity
LLM judge: scalable rubric-based triage, calibrated against human labels
Online: shadow traces, canary guardrails, user outcomes and rollback

Use a separate judging model where helpful, but judges can be biased or inconsistent. Sample for human adjudication and measure judge disagreement. Offline gains do not prove a production improvement: distribution, permissions, and latency all change under real traffic.

6. An engineer's debugging workflow

If an evaluation fails, inspect one traced request from source ingestion to output. Did the authorized current evidence exist? Was it retrieved? Did the context packer retain it? Did the answer use and cite it accurately? Did any deadline or revocation gate intervene? Assign the bug to the first broken stage. Update the golden set with an incident regression, fix the owning component and re-run the same frozen benchmark plus independent test examples.

For side-effecting agents, also score tool arguments, policy permissions, idempotency behavior and ambiguous outcomes: a linguistically correct explanation cannot excuse an unauthorized or duplicate action.

Interview-ready explanations

Mid-level

“I'd start with a small set of real user questions and manually review what a correct answer should look like. Then I'd run the same questions against each version of the assistant and check answer correctness, coverage and citation support separately. I'd include cases where the right behavior is to abstain. If a metric gets worse, I'd trace whether retrieval missed the source or generation used it incorrectly. I'd also keep permission checks as hard failures, not something a quality score can compensate for.”

Senior-level

“Before tuning anything, I'd define what we're trying to improve and which mistakes are unacceptable. I'd build an adjudicated dataset that covers common questions and risky slices, like rare incident codes, stale policies and permission changes. I'd measure retrieval, grounding, completeness, false abstention, latency and cost as separate dimensions. For semantic judgments I'd calibrate a rubric-based evaluator against humans, while enforcing ACLs and tool authorization deterministically. I'd use development data to choose thresholds, then evaluate once on a held-out test set, reporting confidence intervals and segment regressions rather than just an average. After that I'd shadow-test and canary the change with rollback triggers. If the new model answers more questions but creates higher-severity wrong answers, I wouldn't ship it just because aggregate accuracy improved.”
