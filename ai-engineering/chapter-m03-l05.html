Human Approval and Recovery Boundaries

Imagine an agent that drafts a refund for a frustrated customer. The draft looks reasonable, and the model confidently says, “Approved.” Should the money move? Not yet. The model can recommend an action, but an authorized person—and trusted application code—must decide whether it is allowed to happen.

What you'll learn

  • Turn a human approval into an enforced, auditable state transition.
  • Bind approval to the exact operation rather than a vague instruction.
  • Recover safely when a worker crashes, permissions change, or a payment API times out.
  • Explain these tradeoffs naturally in mid-level and senior-level interviews.

1. Start with a real engineering problem

Your support agent reads a complaint and proposes a $120 refund to order 5812. It has permission to prepare a draft but not to move funds. The UI presents the proposed recipient, amount, order, and reason. The customer-support supervisor reviews the details and approves this one refund.

Now imagine the agent changes the refund amount to $1,200 after that approval. If the system only stores approved=true, the larger payment may go through using a decision the supervisor never made. This is why approval must be tied to the exact action, not just the agent run.

Keep three responsibilities separate

  1. The model proposes: “Refund $120 for order 5812.” Treat the proposal as untrusted data, even when the model sounds certain.
  2. The human decides: An authenticated, authorized reviewer sees the complete operation and explicitly approves or rejects it.
  3. The controller enforces: Trusted code checks the decision, payload, current permissions, and execution status before calling the payment provider.

These boundaries also protect against prompt injection. A malicious message saying “ignore approval rules” is still just content; it cannot manufacture an approval record in your database.

2. Approval is a state machine, not a chat message

The controller moves through a small number of well-defined states. A worker may draft a proposal, but only an authenticated approval endpoint can make it eligible for execution. Rejection and expiry are terminal for that approval: a changed proposal needs a new decision.

This diagram shows the happy path. Real systems also need REJECTED, EXPIRED, FAILED, and UNKNOWN. The last state is crucial: it means the external action might have happened, but the system has not confirmed the outcome.

What should an approval record contain?

Store an operation ID, tenant or resource scope, canonical payload digest, approver identity, time, expiry, decision, and a policy/version reference. Authenticate the approver independently of anything the agent says. Before execution, verify that the stored digest matches the payload about to be sent and that current authorization still permits the operation.

An idempotency key lets the provider recognize the same logical operation if the request has to be repeated. It does not replace authorization, and it only prevents duplicates when the provider actually honors that key.

3. Explore three failure scenarios

Choose a scenario and trace the controller's decision. The key question is always: “What do we know for certain, and what must we check before changing the outside world?”

Why a timeout is different from a failure

Suppose the payment provider charges the card and sends a successful response, but the response is lost in the network. Your worker sees a timeout. Retrying immediately could charge the card twice if the provider doesn't enforce idempotency. Instead, persist UNKNOWN and reconcile through a trustworthy read API or webhook. If that evidence is unavailable, stop automatic retries and send the operation to a human review queue.

This can feel less convenient, but it's an intentional tradeoff: for high-impact writes, avoiding a duplicate charge matters more than getting a quick answer.

4. How to make the boundary reliable

In a single-process demo, a boolean check seems enough. With multiple workers, delayed queues, and restarts, it isn't. Two workers might both see “approved” and race to execute. Use a database conditional update so only one can claim the operation, and carry a monotonic fencing version into the execution workflow when possible. After a lease expires, a stale worker must not be able to act on an old approval.

For example, a durable transition from APPROVED to EXECUTING should succeed only if the expected version still matches. If the compare-and-swap fails, that worker stops. The controller then checks the current policy, expiry, scope, and payload digest. The external provider still needs its own idempotency or reconciliation strategy, because a local database transaction cannot atomically commit with an unrelated payment API.

Safe to automate

Read-only lookups; retries for verified transient failures; duplicate requests where the provider has a documented idempotency contract; read-only reconciliation of uncertain writes.

Needs extra care

Payments, emails, account deletion, production deploys, permission changes, or any non-reversible side effect. Keep exact approval, durable state, and a path for manual reconciliation.

Also decide which operations need one approver or two, how long decisions remain valid, who can revoke them, and whether current permission changes invalidate older approvals. Those are policy choices, not model prompts.

5. Python lab: reject stale or mismatched approval

This small, runnable example models the authorization boundary. It intentionally does not call a provider or pretend to solve cross-service atomicity. Paste it into approval_lab.py and run python approval_lab.py.

from dataclasses import dataclass
from hashlib import sha256
import json

def digest(payload):
    canonical = json.dumps(payload, sort_keys=True, separators=(",", ":"))
    return sha256(canonical.encode()).hexdigest()

@dataclass
class Approval:
    operation_id: str
    payload_hash: str
    expires_at: int
    approver: str

def can_execute(operation_id, payload, approval, now, reviewer_allowed):
    return (
        approval.operation_id == operation_id
        and approval.payload_hash == digest(payload)
        and now < approval.expires_at
        and reviewer_allowed
    )

proposal = {"order": "5812", "amount_cents": 12000}
approval = Approval("refund-5812", digest(proposal), 200, "supervisor-7")
assert can_execute("refund-5812", proposal, approval, 100, True)
assert not can_execute("refund-5812", {**proposal, "amount_cents": 120000},
                       approval, 100, True)
assert not can_execute("refund-5812", proposal, approval, 201, True)
assert not can_execute("refund-5812", proposal, approval, 100, False)
assert not can_execute("refund-other", proposal, approval, 100, True)
print("Approval boundary tests passed")

Your task: Add a durable status and version. Implement a conditional claim that only transitions APPROVED → EXECUTING once. Add tests for two competing workers, duplicate delivery, expired approval, and a timeout after the provider has possibly committed.

See the expected recovery behavior

After a timeout, store UNKNOWN with the original operation ID and provider idempotency key. Query the provider before retrying. If the provider confirms success, mark EXECUTED; if it confirms no operation occurred and a replay is explicitly safe, retry under policy. Otherwise request manual reconciliation. A local in-memory example cannot guarantee this behavior after a crash; a real implementation needs durable storage and the provider's documented semantics.

6. Interview-ready answers

These are meant to be spoken aloud. Notice the pattern: begin with a concrete distinction, explain the failure mode, then describe the safeguards and tradeoffs.

Mid-level: “How would you add human approval to an AI agent?”

“I'd have the agent create a draft instead of executing the action right away. The review screen would show exactly what it plans to do—for example, which order it's refunding and the amount. When an authorized reviewer approves it, the backend records that decision for that specific operation. Before making the payment call, the backend checks that the proposal hasn't changed and that the approval is still valid. I wouldn't let a message from the model count as approval, because the model should propose actions, not grant itself permission to execute them.”

Senior: “How do you make approval and execution safe at scale?”

“I'd separate the approval decision from execution and model both as durable state transitions. Approval would be bound to the operation ID, exact payload, reviewer, scope, and expiry. At execution time I'd recheck authorization and use a conditional write so competing workers can't both claim the job. I'd also assume workers can crash and that the external provider can succeed even when our request times out. So I'd use a stable idempotency key when the provider supports one, track uncertain outcomes explicitly, and reconcile them before another attempt. If we can't determine whether a payment happened, I'd rather escalate it than risk charging twice. I'd make the full decision and recovery path auditable.”

Senior follow-up: “Does a short-lived token solve approval revocation?”

“Not entirely. A token that's valid for another few minutes can still authorize actions after someone's permission has been revoked. For sensitive operations, I'd check the current server-side policy at the execution boundary. If that authorization service is unavailable, I'd fail closed rather than treating the outage as permission. If latency is a concern, we can discuss a policy-approved bounded cache, but its freshness guarantee needs to match the risk of the action.”

Practice: Explain how the design changes for sending a marketing email instead of charging a payment. Which failure modes remain? Which safeguards could be lighter?
