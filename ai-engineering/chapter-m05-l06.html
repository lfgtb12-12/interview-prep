Evaluation & Experimentation · Lesson 6

CI Evaluation Gates, Regression & Production Monitoring

A new support assistant improves its average score. CI turns green. But requests from a rarely used service are now answered incorrectly. What should stop that release?

Learning goals

Build versioned evaluation fixtures, define deterministic hard gates and slice-level quality gates, compare paired regressions, validate telemetry completeness, and connect offline CI with production monitoring. This chapter continues agent and tool-use evaluation: a safe-looking final answer is not proof that an agent respected its tool contract.

1. Turn an evaluation dataset into a reproducible release contract

Pin the dataset, ground-truth labels, grader implementation, prompt, retrieval index snapshot, model/provider version and tool schemas to the candidate build. An unexplained judge-model upgrade can change scores with no change in product quality. Separate a small fast smoke set from a larger held-out regression set; keep difficult historical failures as permanent adversarial fixtures. Inspect freshness and possible contamination before interpreting improvements.

Use one task as the denominator in this example, not individual tool calls or repeated retries. Give each task a stable ID and a defined expected result. If an outcome cannot be observed, retain that missing case in the coverage calculation. Do not silently discard it to inflate success. For stochastic agents, use declared repeated runs and report variation, rather than treating one generated trace as certainty.

2. Different failures need different gates

GateExampleRelease treatment
Hard policyUnauthorized tool call, invalid schema, unapproved external writeBlock independently of accuracy
Trace integrityMissing required reconciliation after UNKNOWNBlock or quarantine affected candidate
Quality floorCorrect outcomes for each predeclared task sliceBlock when below threshold
Paired regressionPreviously passing tasks now failCompare on same frozen cases; review important losses
BudgetsLatency and per-task cost exceed a declared capBlock or require explicit exception
CompletenessNew candidate lacks a trace or outcomeInvestigate before claiming a pass

Do not collapse these into one weighted grade: a ten-point quality lift must not purchase permission to leak another tenant's data. Quality thresholds and budgets in this lesson are illustrative; production thresholds come from a documented risk and service contract.

4. Prevent test-score gaming

CI should retain a frozen holdout and add new failure cases deliberately, through a reviewed labeling process. If engineers iterate against the same visible examples every day, the holdout can become a training set by proxy. Use shadow comparisons, blinded adjudication and carefully controlled refreshes. Report both improvements and regressions per task and per high-risk slice; do not hide losses behind the average. A tiny segment's 100% observed pass rate should not be treated as precise evidence of reliability.

For subjective labels, freeze the rubric and calibrate against human-adjudicated cases. A deterministic permission gate should use runtime evidence instead of an LLM judge's opinion. Keep the judge's disagreement, invalid outputs and review coverage visible. A model-reported “confidence” is not a calibrated probability without independent calibration.

5. CI passes; what changes in production?

Offline tests check known fixtures; production introduces new users, drifting runbooks, changed permissions, slow dependencies and novel injection patterns. Start with shadow mode for candidate-vs-current outputs and costs, then a limited canary that actually serves users with strict rollback triggers. Shadow mode cannot measure user-behavior improvements because users do not receive its output. Canary exposure and rollback require reliable routing and version tags.

Instrument traces with request ID, version, tool, outcome category, elapsed time, token/cost estimates, source and permission-check result; avoid storing secrets or raw sensitive content. Monitor user outcomes with carefully defined eligible denominators, safe abstention, invalid tool calls, UNKNOWN side effects, unresolved reconciliations, permission denials versus verification outages, retries, latency percentiles, cost, and feedback sampled for human review. Group by service, tenant class and task type; alert on missing telemetry, not just bad observed scores.

An elevated 403 count could reflect correctly blocked attacks; a 503 from an unavailable authorization backend is a different operational issue. Neither should be silently folded into “incorrect answers.” Review on-call playbooks: pause rollout, inspect traces, query authoritative write state, disable unsafe actions, roll back the version and preserve investigation evidence.

Interview-ready explanations

Mid-level · “What would you put in an AI evaluation CI pipeline?”

“I'd start with a versioned dataset of realistic tasks and known failure cases. For each candidate, I'd run it against the same cases, validate tool calls and permissions, compare quality by task type, and check latency and cost. I'd block releases for safety violations even if the average accuracy improves. I'd also check that traces and outcomes are complete—missing results aren't passes. Once CI is green, I'd use a canary and keep monitoring the same failure categories in production.”

Senior-level · “Your offline eval improves, but production complaints increase. What now?”

“First I'd check whether the deployed model, prompt, retrieval snapshot and tools match the evaluated artifact. I'd compare traffic mix and telemetry coverage, then break down complaints and task outcomes by slice. I'd inspect agent traces and authoritative side-effect state rather than trusting final answers alone. If there's a permission or repeated-write risk, I'd disable that action or roll back immediately. I'd reproduce the new failures as labeled test cases, decide whether the holdout or rubric needs revision, and only resume a guarded rollout once both offline gates and live guardrails are healthy. The CI score is a launch input, not a guarantee.”

Key takeaway

Version the evaluation contract, separate hard safety gates from statistical quality, preserve denominators and slices, and monitor the production system for failures the holdout never saw. A green CI result allows a controlled next step; it does not replace runtime enforcement or incident response.
