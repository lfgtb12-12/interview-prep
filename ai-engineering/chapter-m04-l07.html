RAG & Information Retrieval · Capstone lesson 7

Advanced RAG System Design & Implementation

You've built each piece of a RAG pipeline. Now design the whole service: credible answers from changing, permissioned runbooks, with observability, deadlines, failure isolation and a tested reference implementation.

Capstone goals

Explain an end-to-end architecture for the engineering runbook assistant, trace one payment retry request, defend freshness and access-control boundaries, demonstrate graceful degradation, and practice a complete senior-level design answer.

Offline: revisions → chunks → lexical + vector indexes
Online: auth → hybrid retrieval → rerank
Context → claim validation → cited answer / abstain

All interactive timings are illustrative fixtures, not service benchmarks. The Python lab is a dependency-free miniature, not a deployable payment-policy engine.

1. Start with requirements, not a vector database

Design an internal engineering assistant for the payment, survey, and on-call teams. Engineers ask about incident codes, idempotent charge retries, and current operational policies. Functional needs: answer with source-linked evidence, abstain when policy is uncertain, and let engineers follow citations to the exact revision. Non-functional needs: enforce per-document authorization, support deletions and revocation, keep tail latency bounded, and withstand search or model outages. Agree on measured targets with stakeholders rather than pretending arbitrary thresholds are proven SLAs.

The architecture has two independent flows. Offline ingestion validates source versions, extracts structured content, chunks it, preserves ACL and provenance, and updates both lexical and dense indexes. Online serving authenticates the caller, selects authorized candidates, fuses and reranks, assembles evidence, verifies claims and citations, and returns an answer or an explicit failure mode.

2. Keep ingestion and serving consistent

Source revisions arrive as events, but event delivery can be duplicated or reordered. A worker must compare monotonically increasing source revisions, reject stale writes, and treat deletions as versioned tombstones. Index rows carry source ID, chunk ID, revision, content hash and ACL policy revision. Updates should be staged and published as a consistent visible snapshot when practical.

Index freshness is a correctness concern, not just an operational detail. A runbook updated to forbid a risky replay cannot remain searchable as the former permissive version. Monitor source-to-index lag, failed deletions, and divergence between lexical and vector snapshots. Durable reconciliation handles partially updated indexes.

3. Put authorization before model exposure

A caller's identity and permissions come from trusted application infrastructure, not the prompt. The retriever filters by tenant and source policy before text is delivered to ranking models or answer generation. Revalidate permissions and revisions when assembling context and immediately before rendering citations. Cache authorization only under policy-approved bounded freshness rules; revocation requirements determine what is acceptable.

Never let a retrieval filter failure broaden visibility. If the authorization service cannot verify a sensitive document, fail closed for that document or for the whole answer when required. Returning “retrieval unavailable” is different from “no matching documents.” Authorization correctness is a blocking release gate.

4. Two-stage retrieval balances breadth and precision

First stage: lexical BM25 catches exact identifiers such as PAY-503, while dense retrieval catches paraphrases like “did a timed-out charge complete?” Merge authorized candidate lists with reciprocal rank fusion and deduplicate source chunks. Second stage: a cross-encoder evaluates query-passage pairs on a bounded pool, then a context packer selects diverse, current evidence within a token budget.

Tune branch depth, RRF weights, rerank pool and context k using a judged holdout. No reranker recovers a passage missing from the candidate union. Query rewriting helps acronyms and compound questions but costs latency and can change intent; retain original identifiers, scope and negation. Never treat a high relevance score as proof a cited claim is true.

5. Treat generation as untrusted proposal

Assign citation handles in code, ask the generator for an answer with claim-level source IDs, then verify each handle against current permitted provenance. A separate evaluator or calibrated human labels can assess semantic support; deterministic validation can enforce structure and authorization, not prove entailment from arbitrary text. Unsupported claims should be withheld rather than polished into confidence.

A runbook could contain hostile instructions masquerading as system policy. Retrieved documents are data. They cannot authorize tools, change guardrails or compel disclosure. Protect prompt boundaries, do not expose secrets in context, and log safe IDs rather than unredacted sensitive passages.

6. Graceful degradation is a design decision

A vector index outage may allow an authorized lexical-only fallback if labeled evaluations show acceptable quality for the query class. A reranker outage may allow first-stage ordering within a conservative evidence threshold. But if both retrieval paths fail, or source revisions cannot be trusted, signal unavailability and abstain from policy assertions. Generation without evidence is not a safe fallback for charge replay.

Set an end-to-end deadline and reserve time for authorization, verification and response. Under overload, shed optional rewriting and bound rerank candidates, but never drop trusted security checks. Use concurrency limits, retries with timeouts, circuit breakers and observed failure modes. Keep unknown or conflicting evidence visible to the user instead of inventing policy.

7. Evaluate each stage and explain trade-offs

The launch gate should include candidate recall@k, context recall@k, nDCG, citation support, completeness, correct abstention, ACL tests, revision freshness and full-request p95 latency. Slice by rare error codes, paraphrases, outdated revisions, revoked roles and malicious documents. Compare lexical-only, hybrid and reranked baselines under the same security policy and cost budget.

Trace with request ID, index revision, source IDs, branch ranks, gate decisions and stage timings. Shadow test changes, canary a small percentage, and define rollback triggers before rollout. Add real incident regressions to the evaluation set. A senior design answer should defend why each expensive or complex component earns its place.

8. Walk through an incident end to end

An engineer asks, “PAY-503 timed out; may I replay this charge?” The request is authenticated. BM25 retrieves the exact incident code, dense retrieval finds retry policy, and RRF merges candidates. The reranker prioritizes the current payment safety runbook; the context builder filters duplicate chunks and checks revision/authorization. The generator proposes: “A timeout does not establish failure; check status by idempotency key, then reconcile unknown outcomes.” The checker validates support and links the exact runbook revision.

Now change the conditions. If PAY-503 is missing from the index, fix ingestion or lexical tokenization; do not tune the generator. If the runbook is revoked, refuse to use its text. If a cited sentence contradicts the recommendation, block that claim. If retrieval is down, say so. Every failure has an owning stage and an observable signal.

Interactive architecture resilience simulator

Change the operating condition, the optional single-backend fallback policy, rerank pool size and request deadline. Watch the pipeline nodes and budget bar change. Investigate the stages responsible for the first safe failure instead of relying on the language model to improvise.

Interview answer: design the whole assistant

Mid-level explanation

“I'd prepare the runbooks ahead of time by extracting content, creating chunks, and indexing both keywords and embeddings, along with source revisions and access permissions. When someone asks a question, I'd authorize the caller and search only the documents they can access. I'd merge lexical and semantic candidates, rerank a small set and pass the best current excerpts to generation. The answer would cite those excerpts, and I would check that the citations are valid and actually support the claims. If I can't verify the policy, I'd say so rather than fill the gap with a plausible guess.”

Senior-level system design response

“I'd start by clarifying the knowledge sources, access-control model, source update rate, expected QPS and p95 target, then define hard safety requirements. I'd separate ingestion from serving: ingest revisions idempotently, preserve provenance and ACL metadata, write versioned lexical and vector indexes, and handle deletes with tombstones and reconciliation. For queries, trusted code authenticates and filters before text reaches any model. I'd use BM25 plus dense candidates to cover exact incident codes and paraphrases, fuse rankings with RRF, deduplicate, and rerank only a bounded shortlist. A trusted context assembler would recheck source revisions and permissions. I'd ask the generator for cited claims and verify provenance and semantic support before returning the answer; where support is missing, I'd abstain or return a grounded partial answer. I'd design explicit responses for missing evidence, outages, stale data and revocation. In production I'd trace source IDs through every stage, alert on ACL violations and freshness lag, and measure candidate/context recall, citation precision, false abstention, full-request p95 and cost on a judged holdout. I'd shadow and canary changes with clear rollback criteria. The important point is that the model helps write the answer, but application code owns the trust boundary.”

Follow-up: what would you leave out of v1?

“I wouldn't begin with expensive query rewriting or complex agent loops. I'd launch a narrow pipeline with reliable ACLs, hybrid search, citations and a small judged eval set. I'd only add a cross-encoder or rewriting when measured recall or ordering gains justify the extra latency and operational surface. I'd keep the safe abstention path from day one.”
