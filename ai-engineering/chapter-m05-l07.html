Evaluation & Experimentation · Lesson 7

Evaluation System Design Capstone

Your team is replacing an internal support assistant. The new system retrieves runbooks, looks up incident logs, and may publish approved actions. Leadership wants to release next week. What evidence would make you say yes—or no?

The interview challenge

Design the evaluation and release system, not just the grader. Success means the right task is completed for the right user, with grounded evidence, valid tool actions, bounded cost and latency, and durable recovery for uncertain writes. The candidate must pass successive offline → shadow → canary gates. A passed gate permits a more informative test; it is never a universal safety guarantee.

1 · Offline: frozen tasks and invariants2 · Shadow: latency, cost, trace completeness3 · Canary: actual user outcomes and rollback

1. Define the contract and the data

Freeze task IDs, adjudicated expected outcomes, retrieval evidence and ACL snapshots, model and prompt versions, tool schemas, evaluator versions, and dataset provenance. Split the dataset by runbook answer, incident diagnosis and authorized write; include rare workflows, abstentions, injection attempts and broken dependencies. Keep a separate held-out set to detect overfitting. Use independent human adjudication for ambiguous outcomes; do not treat a judge-model score as a calibrated probability.

Report task success over all eligible tasks, including refusals and timeouts. Then report groundedness, citation support, tool argument validity, safe completion, cost, latency, and slice coverage independently. A retrieval miss should be identified before blaming generation. A correct final sentence is not enough when a forbidden tool ran first.

2. Architecture and responsibility boundaries

Frozen evaluation casesCandidate runner + tracesDeterministic validatorsHuman-calibrated rubricVersioned scorecardRelease controller

The candidate runner uses sandboxed/mock side effects for offline testing. Independent validators check schema, authorization and idempotency invariants using trusted actor/resource context; they must not delegate permissions to the model. The outcome evaluator compares an observed final state with labeled goals. An audit trail joins case, model, prompt, dataset, evidence snapshot, trace, grader and deployment IDs. Keep sensitive runbook content and tenant data out of unrestricted traces.

Online writes must use server-enforced idempotency and a reconciliation path. If a publish times out, record UNKNOWN and query its durable request ID before considering retry. A trace alone cannot confirm whether a remote write committed. Production guardrails remain active regardless of offline pass rates.

3. Interactive launch review board

Explore ten authored release scenarios. Each phase changes what evidence is eligible to support the decision; controls let you tighten the rare-task floor and required practical improvement. The data are teaching fixtures, not observations from a real deployment.

The online comparison uses one independent binary outcome per randomized user per arm, a fixed horizon and a normal-approximation 95% interval. It is a teaching calculation, not a cluster-aware or sequential inference engine. Do not interpret zero observed incidents as zero underlying risk or bypass rollback on safety incidents.

4. Write down the release protocol

Offline gate: hold out tasks, validate answer evidence and tool boundaries, enforce per-slice quality floors, independently flag unsafe reads and uncertain writes. No weighted accuracy improvement can offset an unauthorized call. Use paired case-level regressions to find what got worse.

Shadow gate: run candidate work with no user-visible response and no actual side effects, compare operational traces, end-to-end deadline, concurrency, cost and failure modes. Check telemetry completeness and version attribution. A shadow pass does not establish a causal change in user satisfaction.

Canary gate: assign independent users or suitable clusters consistently, declare the primary outcome and minimum practically useful gain, precommit duration and stopping policy, and inspect risk slices. A fixed-horizon CI excludes some effect values under its assumptions; it does not give posterior probability. Pause or roll back on permission leaks, duplicate external writes or other critical guardrail breaches independently of the point estimate.

Operations: maintain dashboards for task completion, abstention, citation correctness, invalid tool calls, UNKNOWN outcomes awaiting reconciliation, ACL verification outages, latency percentiles, cost and missing logs. Include runbook owners, rollback controls, audit IDs, alert routing, and a human review queue for novel failures.

Interview-ready answers

Mid-level · “How would you evaluate an AI support assistant before launch?”

“I'd start with a versioned set of realistic support tasks, including difficult and unsafe cases. I'd check retrieval quality separately from answer grounding, then validate the tool calls and final outcome. I'd compare the new and current versions on the same labeled questions, with quality broken down by task type. Authorization and side-effect checks would be hard gates. After that I'd use shadow mode to verify latency, cost and traces, followed by a small canary with production monitoring and rollback ready.”

Senior-level · “The new agent is three points better. Ship it?”

“I'd first ask what those three points represent, who labeled the tasks, whether the holdout was contaminated, and whether the comparison uses independent units. I'd look at the rare-task and security slices before trusting an aggregate. A correct answer does not erase an unauthorized call or an ambiguous external write, so those become hard gates. Offline success would justify shadow testing, not immediate release. Shadow would show operational risk, and an online canary would give us actual user outcomes under a predeclared experiment design. I'd compare the interval with a practical-benefit margin and keep safety rollback independent of statistical significance. I'd only expand traffic when all stages have credible evidence and owners are ready to respond.”

Module 5 synthesis

The evaluator is a system: data collection, labeling, deterministic gates, semantic review, experimentation, release control and runtime feedback. Its most important output is a defensible decision with explicit limitations—not a single impressive score.
