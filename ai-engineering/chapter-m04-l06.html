RAG & Information Retrieval · Lesson 6

RAG Evaluation, Debugging & Operations

A helpful-looking answer is not a quality metric. Learn to identify exactly where a runbook assistant failed—and prove whether a retrieval change makes answers more reliable without breaking latency or permissions.

What you'll learn

We continue the PAY-503 runbook assistant from L01–L05. Build a judged retrieval set; measure candidate and context quality; separate groundedness, completeness and citations; diagnose per-stage failures; and evaluate latency, cost, freshness and production rollouts.

1. Start with a failure, not a pretty dashboard

Our runbook assistant answers “May I replay a PAY-503 charge after timeout?” with a fluent recommendation to retry. The actual runbook says to reconcile an unknown outcome first. We need to know where the system failed: was the runbook missing from the index, retrieved too late, excluded from context, or ignored by the generator? A single “RAG accuracy” number cannot distinguish these problems.

Treat the pipeline as a series of independently observable stages: ingestion → authorized candidate retrieval → reranking → context assembly → generation → citation validation. A trace should connect the user's request to stage outputs using IDs, version stamps, timings and safe evaluation outcomes—not sensitive raw documents.

2. Create a judged dataset that resembles production

For each representative question, capture the authorized role, canonical relevant passage IDs, optional graded relevance, authoritative answer facts, allowed source revisions, and expected response type (answer, abstain, or unavailable). Include exact identifiers, paraphrases, multi-part questions, zero-match cases, revoked access, outdated policies and intentionally injected text.

Keep a locked holdout separate from tuning. Label with domain experts; measure inter-annotator disagreement and adjudicate ambiguous examples. A benchmark with only easy FAQ questions can make a dangerous payment assistant look impressive. Slice all metrics by query class, document freshness and access policy; watch for regressions hidden by global averages.

3. Measure retrieval before judging the final answer

Recall@k is the proportion of known relevant passages present among the first k results; it answers whether the generator has a chance to see the evidence. Precision@k is the proportion of the k returned passages that are relevant; when fewer than k items are returned, use k as the denominator and state that convention. MRR is the mean reciprocal rank of the first relevant result; nDCG@k rewards placing more highly graded sources earlier, normalized by the ideal ordering.

Report candidate recall and context recall separately. A perfect candidate pool is not enough if reranking or token truncation removes the required paragraph. Do not call a hit-rate (any relevant in top-k) recall unless you deliberately choose query-level binary relevance. Evaluate document IDs vs chunk IDs consistently; duplicate chunks can distort scores.

4. Grounding, faithfulness and citation precision are different questions

Once evidence reaches generation, measure whether factual claims are supported by supplied context (faithfulness), whether the answer covers required facts (completeness), and whether cited spans actually substantiate their associated claims (citation precision). A legitimate citation handle can still point to contradictory evidence. A conservative assistant may have zero unsupported claims by refusing everything, yet still fail user needs.

Use human-approved claim/source labels as a baseline; evaluate any automated judge against that set, especially on negation, time changes and hallucinated citations. Also track abstention precision/recall, inappropriate abstentions and restricted-data disclosure. Scores from an LLM judge are estimates, not proofs. Build a dispute queue for important wrong answers.

5. Latency and cost are part of correctness at scale

The retrieval stack has separate latency contributors: query rewriting, lexical/vector fan-out, merge, cross-encoder reranking, evidence lookup, generator and verifier. The end-to-end p95 is measured from request traces; it is not generally equal to the sum of independently measured stage p95 values, because slow stages may not coincide and parallel steps overlap.

Measure p50/p95/p99 per stage and end-to-end, token spend, index costs, cache effects, reranker requests, quality under timeouts and concurrency. Set a global deadline with remaining-time budgets. Under overload, consider smaller rerank candidate sets or bounded rewriting, but never weaken ACL checks or fabricate policy evidence. A timeout should be distinct from a legitimate zero-match result.

6. Debug with controlled experiments, not guesswork

If PAY-503 is absent from candidate IDs, verify source version, ingestion, tokenizer, ACL and query matching. If it appears at rank 30 but is absent from top-5 context, inspect fusion, reranker and truncation. If it reaches context and the answer says “retry immediately,” inspect claim-level grounding and prompt injection defenses. If the answer is correct but cites a survey guide, inspect source-handle mapping.

Change one parameter at a time; compare against an immutable baseline on the same judged queries. Shadow-test new embedding versions and rerankers before replacing production; use canaries and rollback triggers. Store trace IDs and stable source IDs, but redact queries and documents where privacy policy requires. Add tests for failures that actually occurred.

7. Turn evaluation into an operations loop

Define alertable guardrails: unauthorized-context rate must be zero, ingestion lag below a source-defined threshold, labeled supported-claim rate within your measured baseline, retrieval p95 below the service objective, and no sustained increase in stale-source answers. Investigate alert slices before tweaking prompts.

An incident runbook might say: identify failing stage; check index and ACL revision; run a sanitized replay; compare candidate IDs; validate source citations; mitigate by rollback or abstention; write a regression case. During retrieval outages, explicitly return unavailable instead of inventing current policy. Evaluation is a release gate and a feedback loop, not a one-time leaderboard.

Speak it in an interview

Mid-level: How would you evaluate a RAG system?

“I'd begin with a representative set of actual questions and human-reviewed relevant passages. Then I'd measure retrieval recall at the candidate stage and again after reranking and context selection. For the answer itself, I'd evaluate factual support, whether it covers the important facts, and whether each citation supports its claim. I'd also add cases where the right response is to abstain. That tells me whether a failure came from search, context assembly or generation instead of hiding everything behind an overall model score.”

Senior-level: How do you operate and improve RAG safely?

“I'd define quality and operational gates independently. ACL violations are release blockers; a fluent answer cannot compensate for an unauthorized source. I'd build a labeled holdout with slices for rare incident codes, stale revisions, contradictory sources, paraphrases and deliberate injection attempts. I'd trace source IDs and revisions through retrieval, reranking, context and citations, with privacy-conscious logs. For each candidate change I'd compare recall@k, nDCG, supported-claim rate, correct abstention behavior, end-to-end p95, cost and index freshness against a stable baseline. I'd shadow-test, canary and retain rollback. If an answer is wrong, I'd identify the first stage where the correct evidence was lost. During a retrieval outage I'd explicitly signal unavailability, rather than imply there was no policy. That gives us an objective release decision and a repeatable incident workflow.”

Follow-up: What is the trap in measuring stage p95?

“I wouldn't add independent stage p95 values to estimate end-to-end p95. Percentiles don't add that way, and stages may run in parallel. I'd instrument full request traces, measure the actual end-to-end distribution, and then use per-stage timings to locate the bottleneck.”

Quiz · eight questions

1. A relevant passage appears at candidate rank 15 but is excluded from top-5 context. Which stage should you inspect?

2. What does recall@k measure with passage-level labels?

3. Why is a perfect groundedness score not sufficient?

4. Why not add per-stage p95 latencies for end-to-end p95?

5. A cited document exists but does not support its claim. Which metric detects the issue?

6. An ANN update improves average recall but harms PAY-503 searches. What now?

7. The index is unavailable. What should the assistant report?

8. Which signal should be enforced independently of model quality?
